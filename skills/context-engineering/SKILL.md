# Context Engineering

Context is a finite resource with diminishing returns. The goal is **the smallest set of high-signal tokens that maximizes the desired outcome** — not the shortest context, the *highest-signal* one.

This is **one rung of a ladder** — prompt, context, harness, loop — and it is the *during-the-session* rung: what is in the window right now. **compound-v:gathering-context** is the *before-you-build* one: what to go and find. Same discipline, different moment; `references/context-is-the-work.md` has the map.

**Spend tokens first — "lean" is not "always fewest tokens."** Token spend *alone* explained ~80% of agent-performance variance on a measured multi-agent research system's eval; its multi-agent win came from spending ~3.75× the tokens of the single *agent* it beat — about 15× those of a single chat — not from the architecture. Read these as a directional lever, not universal constants: when a result is poor, the first thing to try is usually *more* tokens on the right context — not a cleverer prompt and not more agents. So lean is two moves, not one: cut the tokens that don't change the answer, *and* deliberately spend where compute is the lever.

## When to use

**The gate, so this skill doesn't over-fire:** if a human is driving one interactive agent and cost is not the constraint, the right answer is a minimal prompt plus retrieval tools — not a context-engineering program. This earns its keep at production volume, on long autonomous runs, or under a real cost/latency constraint. On a short single-shot task that comfortably fits, it is pure overhead.

## Why context degrades: rot, measured

As tokens grow, the model's ability to **accurately recall** any one fact *decreases*. Take this as measured, not explained: the *context rot* benchmarks show loss even on a trivial retrieval task — ~40% down by ~170K tokens on some tasks, far sooner with low-signal filler, and a *single* distractor in the window is enough to move the number. Resist the tidy architectural story about attention arithmetic; the mechanism is not settled, and a wrong mechanism will point you at the wrong lever. Reason from the behavior: it's a gradient, not a cliff, and a bloated context is actively *worse* at the task, not just more expensive.

The flip side: context is also a **capability lever**. Loading the *right* large body — a whole codebase, a domain corpus — can make the model dramatically better at the task, comparable to a jump in model scale, because it's learning in-context.

## Just-in-time retrieval beats pre-loading

Don't dump everything the agent *might* need into the prompt. Keep **lightweight identifiers** — file paths, queries, URLs, IDs — and load the actual content at runtime with tools, the way you `ls` and `grep` instead of memorizing a filesystem. That is progressive disclosure: the agent discovers what's relevant by exploring.

The honest tradeoff: runtime exploration is slower than reading pre-computed data, and a poorly-equipped agent can waste context chasing dead ends. So use a **hybrid** when up-front data buys real speed. Claude Code is the canonical example: it naively drops `CLAUDE.md` into context up front (small, always relevant) while using `glob`/`grep` for everything else just-in-time.

**Shape what retrieval returns, not just when it runs.** A search tool that hands back payloads has rebuilt the dump you were avoiding. Return **locators plus a bounded excerpt** — an absolute `path#Lline` and a few hundred characters — and let the agent open the full body only for hits that look promising. Where one artifact gets read at very different depths (a trace, a long document, a big record), ship **graduated read endpoints** rather than one: condensed stats, a mid-resolution view, the whole thing. All-or-nothing is itself the anti-pattern — with only "summary" and "everything" on offer, an agent needing slightly more than the summary pulls the entire object every time.

### Programmatic tool calling: keep intermediate results out of context entirely
JIT retrieval controls *what* enters context; programmatic tool calling controls whether the *plumbing between tools* enters it at all. When a task chains tools — fetch 200 rows, filter, join, take the top 5 — don't round-trip every intermediate through the model. Have the agent write a few lines of code that call the tools and do the filtering/aggregation in the execution environment, returning only the final small result — the 200 rows never hit the context. The magnitude is real: a worked Drive-to-Salesforce example drops from **150,000 to 2,000 tokens — a 98.7% saving**. Reach for it when a step's raw output is large but its useful distillate is small.

When you *do* pack a large retrieved or assembled payload into the prompt, wrap it in **XML-style tags, not JSON** — tags read like the prose the model trained on and act as navigation anchors in long context, while JSON's structural characters (`{}":,`) are pure token overhead. On a large payload the token savings from the format alone are substantial.

The **tool *set* is always-loaded context too** — definitions sit in the prefix every turn, so a sprawling or ambiguous tool list spends from that same finite recall before the model reads a single request. Carry a minimal, non-overlapping set (compound-v:designing-agents owns the interface rules); when you genuinely need many, expose them progressively (a `search_tools` call, or tools-as-files read on demand) rather than dumping every definition up front.

## Order context by volatility (static prefix → dynamic boundary)

**The cache economics invert the naive trim-to-save-money reflex.** Uncached input costs roughly **10×** cached input, and cache validity is prefix-scoped: a change *early* in the prompt re-prices everything after it. So shaving 500 tokens off the top of a stable system prompt can cost more than it saves — it invalidates the entire cached span behind it in exchange for one turn's worth of savings. Hence the layout rule: **stable, shared content at the very front; volatile, per-task content at the end**, split by an explicit boundary. **Treat cache hit rate as a first-class metric** — alert on it the way you alert on uptime, because a silent drop shows up as a cost and rate-limit problem long before anyone calls it a bug. Well-built coding agents measure in the 80s; the best measured sits around 92%, so treat the 80s as the working range and a sharp fall as an incident. A 0% hit rate is almost always one cause: a timestamp in the system prompt.

- **Static prefix (cacheable):** base instructions, tool descriptions, the verification checklist, durable conventions. No timestamps, no per-request data.
- **Dynamic suffix (not cached):** cwd/OS, today's date, git status, the live conversation, retrieved files.

Claude Code does this literally, splitting its system prompt on a `__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__` sentinel — blocks before it are eligible for cross-session caching, blocks after are not.

## The compaction ladder (climb only as far as you need)

**Every rung here is an in-window lever; the cause often sits outside it.** A task that compacts, re-gathers and compacts again is short of *locality*, not of window: understanding one change means assembling modules from three directories, which is what interfaces exist to prevent. **The trap: indirection is not locality** — an interface you chase through four files costs the gather it saved.


**Attribute before you cut.** When the working window passes ~100K tokens (absolute: a 1M window lifts it far less than fivefold), break it down by consumer first — system prompt, tool schemas, message history, retrieved content, memory files — and pull the lever for whichever one is actually fat. Summarizing the transcript does nothing about a bloated tool block; that is fixed by carrying fewer tools. Never estimate that block — **run `/context` on an empty session** and read it per *server*: one official MCP server read 46.2k tokens of a 200k window before any work.

1. **Observation masking — do this first.** Keep the full history of *actions and reasoning*, but replace older *observations* (tool outputs) with placeholders, retaining only the most recent ~10 turns of full observations. Measured result: **52% cheaper with a +2.6% solve-rate improvement** — as good as full summarization at a fraction of the cost. Old tool outputs are rarely re-read, but old reasoning still informs current decisions. **Never tidy failures out of context.** When the model sees a failed action *and* the error it produced, it updates away from similar actions; delete the failure and you delete the update, so it cheerfully repeats the failure. Mask resolved noise, not the live failure it's still working — and the rule holds at every boundary: observation masking, the compaction summary, and what a sub-agent reports to its parent all have to preserve what was tried and why it was abandoned. More broadly — **keep failures, distrust successes:** giving an agent its *past failure cases* measurably improves performance (it breaks out of local minima), while feeding it *past successes* often backfires — the agent pattern-matches the prior answer, gets lazy, and slips back into a local minimum.
2. **Tool-result clearing — mechanical, but not free.** Replace consumed `tool_result` bytes with a literal marker like `"[cleared to save context]"`, while **keeping the `tool_use` record** so the agent still knows *what action it took*. It needs no model call — this alone took one workload from 335K peak tokens to 173K — but under a prompt cache any edit to old history re-bills everything cached after it, so batch clears and masks big enough to pay for that miss, never one per turn. When you *truncate* instead — keeping only the head and the recent tail — leave an explicit gap placeholder ("skipped N messages") at the seam, because silent truncation makes the model reconstruct the missing span and hallucinate. **Keep the pointer when you drop the payload.** A fetched page's content can leave the window as long as its URL stays, and the pre-compaction conversation as long as the summary names its transcript file — Claude Code's does, so grep that file before re-deriving a detail the summary dropped. A reference is lossless in a way a summary never is — so prefer drop-with-a-reference to summarizing whenever the content is re-derivable.
3. **Summarizing compaction — costs one model call, so do it later.** Near the window limit, summarize the conversation and reinitialize with the summary. Carry **the user's own messages verbatim**, within a budget — the record of every correction and change of intent, which a summary paraphrases away — then preserve **architectural decisions, unresolved bugs, and implementation details**; discard redundant tool chatter. Tune by **maximizing recall first, then precision**. A workable stacked recipe: clear tool-uses at ~50K input tokens (keep the 6 most recent, never clear memory results), compact at ~180K.
4. **Carry critical state deterministically — never trust the summary to hold it.** Keep a `NOTES.md` / `todo.md` / progress file *outside* the context, and re-read it after a reset. Structured state (the plan, TODOs, open questions, hard constraints) must be carried by code, not entrusted to summary prose — full rewrites of a memory doc corrupt unrelated fields, so prefer targeted updates.

**Compaction eats your instructions, not just the chatter.** The procedure the agent is following lives in the window too, and a summarizing pass drops it as readily as a tool dump. Claude Code restores invoked skill bodies up to 5,000 tokens each and 25,000 in all, oldest dropped first, and re-reads only five of the files it touched this session, most recently *modified* first, so once five files are edited a reference the stage only read is gone — which is how a run can evict the procedure mid-run and drop a stage with every health signal green. **Don't hold the whole procedure resident** — keep a thin router in context and load each stage's instructions at the moment it runs, so there is less standing instruction for compaction to take. And **treat the compaction boundary as a reboot**: re-read and re-inject the instruction file, the state file and the running stage's reference *after* the summary rather than trusting the summary to have carried them (harnesses expose a hook that fires on compaction for exactly this).

**Goal recitation is about position, not durability.** Re-writing the objective into the *tail* of the context puts it inside the model's most recent attention span, which is what counters lost-in-the-middle drift on a long run. The state file is what makes the goal durable; the rewrite is what makes it *attended*. Do it after every compaction and at each work-unit boundary, not once at the start.

**Durable state survives a crashed window.** The transcript is ephemeral and capped by the window; the workspace persists across as many windows as the task takes — so treat it, not the transcript, as the agent's real memory. The progress file from step 4 is half of this; **git is the other half.** Commit at each clean checkpoint. If a window dies mid-task — runs out, gets compacted badly, derails — the next one recovers by reading `git log`/`git diff` rather than reconstructing intent from a lossy summary.

### Compaction as a deliberate cadence, not a panic button
Compact *proactively* between work units — after a sub-task lands and before the next begins — so each unit starts on a clean, intentional summary instead of a window that's 90% full of the previous unit's noise. And put a circuit breaker on the compaction loop itself: abort after a few consecutive failures (3 is a reasonable default) rather than retrying forever — a loop that can't produce a valid summary and won't stop will burn API calls indefinitely (bounded retry — compound-v:make-it-stable).

One hard rule for any summary: **it must never assert a completion that wasn't confirmed.** A summary that says "tests pass" when they were never run hands the next window a false premise it will build on. Mark unconfirmed steps *in-progress*, never done.

### The agent-readable instruction file (`CLAUDE.md` / `AGENTS.md`): persist durable facts, keep it small
When a session discovers a fact the *next* session will also need — the build command, a non-obvious env quirk, a directory that's load-bearing — write it to the repo's agent-readable file so the next session boots already knowing it instead of re-deriving it. **Hard guard: this is one markdown line in a file the agent reads at startup — not a database, not a vector index, not a memory framework.** A retrieval system around it reintroduces the cost and failure surface you were avoiding.

Gate the write — persist only a fact that is (a) durable (still true in future sessions, not just this run), (b) general (helps future tasks, not only this one), and (c) safe to commit. **Never save:** transient failures or a one-off error you already fixed; secrets, tokens, or credentials; anything task-specific that's noise outside this run. **Cache what's expensive, not what's interesting.** *Necessary* knowledge exists nowhere else — a user preference, a decision that was made, a constraint you were handed — so store it. *Compiled* knowledge is re-derivable by reading the code; store that only when it is both frequently accessed and expensive to recompute, and evict it once it goes unread. The success metric for any memory layer is *the same answer with fewer tool calls or tokens* — if it doesn't move that number, delete the layer.

**Structure it by scope.** The file governs its directory subtree: one root file for repo-wide rules, a nested file only where a subtree genuinely differs — deeper files win, and the chain from repo root down to the working directory is preloaded (the open `AGENTS.md` spec). Claude Code loads a `CLAUDE.md` deeper than that only once a file under it is read, and by default skips `AGENTS.md` when a `CLAUDE.md` sits at or above the working directory — write each fact where the harness loads it. Hold only what's durable and load-bearing for *acting on the code*: build/test/run commands, a map of how the code is organized, naming and style conventions, the non-obvious env quirks. Not a tutorial, not prose.

**Maintain it like context, because it is.** The file is always-loaded — every line is paid from that same finite budget on *every* turn, so a fact-dense short file beats a complete long one: prune stale rules, merge duplicates, and push rarely-needed detail into a doc the agent reads only when relevant. Keep **one source of truth** — each durable fact lives in exactly one artifact and every other doc *links* to it instead of restating it; never restate what the code, tests, or config already assert. Reconcile on a cadence — append-only growth is rot — and treat any persisted fact as a **hint, not ground truth**: the moment the code or the user contradicts it, fix or delete that line rather than act on it.

## KV-cache discipline (where the cost actually is)

Agent traffic runs roughly **100:1 input-to-output tokens**, so the input cache matters ~100× more than output length. To keep the cache warm:

- **Append-only in the steady state** — don't edit or reorder a previous turn; any change downstream of a cached span invalidates it. The exception is repair: if the history contains a tool call with no matching result, re-pair them before resuming, because a provider will reject that history outright.
- **Deterministic serialization** — sorted JSON keys, stable formatting, so prefixes are byte-identical request to request.
- **Mask a tool's logits to steer a *trusted* agent off it; remove the tool outright when the input is untrusted.** Masking keeps the prefix byte-identical, which is why it's the cheap move — removing a tool changes the prefix and busts the cache for everything after it. But masking is a *cache* optimisation, not a trust boundary: a masked tool is still sitting in the context, so an injection can still reach for it and a runtime permission gate still has to be the thing that says no. On untrusted input, drop the privileged tools entirely and accept the cache miss — a tool the agent doesn't have cannot be talked into being used (compound-v:agent-security).

**On a fork (a sub-agent, a retried turn, or the compaction call itself), copy the parent prefix byte-for-byte** — one differing whitespace or reordered field means a cache miss on the entire shared span, so the fork pays full price for context it could have inherited.

## Sub-agents are context firewalls

This is the mechanism the rest of the kit refers to. A sub-agent runs in its **own separate context window**; the parent sees *only the final summary it returns*. Every intermediate read, search, failed attempt, and tool dump happens inside the child's window and **never enters the parent's** — the boundary is a one-way valve that passes a distilled result and blocks the raw byte-stream that produced it. So delegate the token-heavy, noisy work — deep exploration, large searches, browser sessions, reading a sprawling codebase — to a sub-agent and get back a distilled ~1–2K-token digest.

The discipline that makes it hold: **findings cross the boundary, raw documents do not.** The parent holds the high-level plan and synthesizes; sub-agents do the messy gathering and report conclusions, not transcripts. One carve-out, per the failure rule above: *a dead end and why it was abandoned is a finding.* **And the valve is right for a child that read, wrong for a child that acted.** Reading produces findings, which compress cleanly. Acting produces *implicit decisions* — the theme it picked, the edge case it waved through, the pattern it followed — and a summary is precisely where those die, so the parent never gets to overrule the one it would have. That asymmetry is why the safe shape is read-only sub-agents plus a single writer, and why a harness that does let a child act ships a way for the parent to **read the child's trajectory**, not just its conclusion. So when the child changed something, keep its trace reachable — a path, a diff, a log the parent can open on demand — and treat the digest as an index into it. (For *whether* to fan out and how to brief workers, use compound-v:dispatching-parallel-agents; for choosing the agent *shape*, compound-v:designing-agents.)

## Right-altitude system prompts

When you do put instructions up front, aim between two failure modes: too *brittle* (hardcoded if-else logic that overfits and rots) and too *vague* (high-level prose that assumes shared context the model doesn't have). Start from a minimal prompt on the best model, then add instructions and examples to fix observed failure modes — don't pre-write guards for problems you haven't seen.

**Contradiction is more expensive than vagueness.** Conflicting instructions don't just get resolved arbitrarily — the model burns reasoning tokens trying to reconcile them, and a single conflicting piece of context has sent a model into roughly half an hour of deliberation. **The signature of a context conflict is a latency blow-up, not a wrong answer** — so when a context change makes things slow rather than incorrect, go looking for a contradiction. Fix it by ordering (state which instruction wins) or by an explicit carve-out; never leave two live rules that disagree. So **measure time, not only accuracy** on any context change: one that holds accuracy while tripling deliberation is a regression an accuracy-only eval scores as neutral (compound-v:evals).

## Encode what transfers across models; defer what scale washes away

The harness is the durable asset; the model is swappable — so spend effort on what *survives* a model upgrade and let the model handle what it'll soon do unaided. **Encode** the things that transfer across generations: verifiable environments and checks, the plan/state/conventions, agent-addressable structure, and representations that turn a fuzzy task into one the model is already strong at. The sharpest version of that last one: **make a non-coding task look like a coding task** — hand the agent files plus `bash`/`grep` over prose-described data instead of a bespoke tool-for-every-step, because coding-agent training generalizes to anything shaped like filesystem ops. **Don't encode** elaborate cognitive scaffolds, role-play personas, or hand-built planners that the next model will simply absorb — that work gets washed away. The test when unsure whether to build a mechanism: would it still earn its place against a clearly smarter model? If no, defer it.
