# Batched Implementation

Run a plan as a small number of fresh-context implementer subagents (one per 2-3 related tasks), recheck each batch, and keep going without stopping to ask permission.

## When to use

- You have an approved plan (from compound-v:writing-plans) or a concrete task list, and you're about to build.
- The work is the **Standard** tier (a feature, ~2-8 tasks). For a one-file change or a typo, skip this entirely and just do it inline → compound-v:verification-before-completion. Spawning a subagent for a one-liner is the overkill this kit exists to refuse.
- For **Large** work (multiple subsystems), decompose into sub-projects first; each runs its own Standard cycle.

## Why batches, not one-agent-per-task

A fresh agent per task, plus two sequential reviewers, plus a final review is ~16 dispatches for a 5-task plan — and that 1:1 ratio is justified only by fear of context pollution. Size the batch by **recheck granularity** instead: a batch is the unit you can review and roll back as one coherent step, and 2-3 coupled tasks is about as much diff as one read-only pass can hold in judgment. Reviewability is the binding constraint, not context capacity. Keeping shared types/imports/helpers in one agent's head also keeps them *coherent* (the same struct named the same way across the tasks that touch it), and for coupled, latency-sensitive work one strong agent beats a planner→executor→critic fan-out — so group coupled tasks together and don't shatter a plan into atomized agents. Batching cuts dispatches ~60% with no loss of isolation: each batch is still a clean context, and recheck (not a second reviewer) is the quality gate.

## The loop

**Setup (once):**
1. **Sanity-check the environment** before building — confirm the verify commands (test/lint/typecheck/build) actually run here. A plan that can't be verified in this session is a plan you'll finish blind. Capture a **green baseline**: run the suite *before* you edit. If it's already red, surface that and stop — otherwise you can't tell a failure you introduced from one that was already there. A static check (lint, typecheck) red across a legacy codebase is the exception: save its current findings as the baseline outside the repo, or use the one the repo already commits — a new suppression file silences those findings for the whole team, which is the team's call — and gate each batch on no *new* finding, because that is the only green such a repo can reach and stopping would halt every run on it. The trap is the baseline: regenerating it to absorb a finding this batch introduced is editing what grades you. **Then make the loop's output cheap:** wrap each check so a pass prints one line and only a failure prints anything, and turn the runner's fail-fast on so the implementer fixes one thing at a time. Unattended length is bounded by how fast the window fills, and a green suite's full output is the most reliably worthless text in the run. The trap: a ✓ is not evidence — this is for the *implementer's iteration loop only*, never the completion gate, where **compound-v:verification-before-completion** still requires reading the output that proves the claim.
2. Confirm you're not on `main`/`master`; if you are, branch first. If the harness already gave you an isolated workspace (a worktree, a fresh clone, a sandbox), use it — don't nest a second one. If it didn't and the work wants isolation, prefer a native worktree, and always branch before the first edit.
3. Read the plan file **once**. Extract every task with its full text and context. Build a TodoWrite with one entry per task.
4. Group tasks into batches of **2-3 by coupling** — tasks that share files, types, or a feature surface go together. A task that's independent of everything else can be its own batch. When a batch's tasks are *structurally similar* (say three near-identical endpoints), the brief must spell out what **differs** per task — a fresh-context implementer falls into a rhythm and adapts the third from the first two, inheriting their assumptions.

**Per batch:**
1. Dispatch **one implementer subagent** (`general-purpose`) for the batch. **Don't pass a `model` parameter** — the worker inherits the session model, which is already the one the user chose; naming a model can silently *downgrade* it.
   - **Paste the full task text** into the prompt. Never tell the subagent to "read task 3 from the plan file" — it costs a read and risks it grabbing the wrong context. The dispatch prompt is the contract; it must stand alone. Same for skills: a subagent *can* invoke this kit's skills, but a cross-reference resolves to whichever installed copy wins, which may not be this one — so when the brief names a skill, paste its operative constraint alongside the name.
   - **Carry the user's approval across the boundary.** If the user approved a specific action, quote their exact words in the brief — the worker's permission check sees only the worker's own transcript, so an approval you received is invisible to it unless you pass it through.
   - Include: the pasted tasks, scene-setting context (what exists, what the batch fits into), the relevant file paths, and **how to verify** (the exact test/lint/typecheck commands). An implementer told how to check its own work produces far less for recheck to catch.
   - **Paste the plan's preamble too — every batch, not just the first.** The global constraints, the deferred list, the divergence rule and the User-Review flag were written for exactly this reader, and they are the part the task text does not carry: a fresh implementer sees only its own tasks and silently regresses any unstated constraint to model defaults. Drop the preamble and you drop the version floors and security rules *and* the instruction to stop and report instead of improvising — so the batch that hits a false assumption grinds on it instead of surfacing it.
   - **Paste the state file's Do-not list too**, when the run carries one (**compound-v:handoff**). A fresh-context implementer *is* the fresh session that section exists to stop: it holds the approaches already tried and rejected, and it is the one part of the run's history the repo cannot hand back. Leave it out and the batch pays full price to rediscover a dead end, then reports it as a finding.
   - Mandate the discipline: follow existing conventions — and when a convention matters, **paste the exemplar** (the file or snippet to imitate) into the prompt, not a bare "follow conventions"; a fresh-context agent regresses to model defaults for any convention it wasn't shown (a good tool/interface definition includes example usage). Never assume a library is present without checking the manifest, write tests (compound-v:test-driven-development), keep changes minimal, stage each commit by explicit path (never `git add -A`, `git add .` or `git commit -a` — the tree may hold the user's or another session's work), and self-review before reporting. If the env can't run the verify commands, the implementer must **say so** in its report — an honest "couldn't run the suite here" beats a fabricated green.
   - **Brief the *what* and the constraints, not the *how*** — paste tasks, exemplars and verify commands, but don't dictate the implementation line-by-line; an over-prescribed brief wastes the implementer's judgment and misses what it would have found, and over-prescription backfires hardest exactly where you hold less of the detail than the implementer will once it's in the code.
   - **Mark a corner at the moment it is cut.** "Keep changes minimal" is how a global lock or an O(n²) scan gets chosen deliberately and then forgotten, so make the deferral addressable rather than remembered: the implementer writes `ceiling: <the limit>, <what would force the upgrade>` on the line, at the time — a later sweep sees the code but never the choice. The trap: a marker naming no condition is the one that rots, so the batch report counts markers and trigger-less markers separately. Distinct from **compound-v:get-shit-done-3-build**'s `TODO`/`stub` scan, which catches what was left by accident.
   - **Write what breaks without it on the line, at the time.** Every guard, special case or workaround the implementer adds carries the failure it prevents — the trigger, what was observed, the incident — because the next reader is a fresh agent most of the time, and it sees a swallowed error as a bug and fixes it unless the line says what that costs. Two things the brief forbids: a comment that restates the code, and any `keep in sync` note — a fact needed in two places gets one source and a parity test, or the batch reports `DONE_WITH_CONCERNS` naming the duplication. Where the implementer is guessing at the why, it writes `[ASSUMPTION]` on the line (compound-v:writing-prd's tag): a wrong reason licenses the deletion. `references/mep-gate.md` → "What the next change reads" carries the form.

2. Read the subagent's report. It must end in one of **four statuses**:

   | Status | What it means | What you do |
   |---|---|---|
   | `DONE` | Built, tested, self-reviewed, clean | Proceed to recheck. |
   | `DONE_WITH_CONCERNS` | Built, but flagged something | If the concern is correctness or scope, resolve it before recheck. If it's a benign observation, note it and proceed. |
   | `NEEDS_CONTEXT` | Missing info it couldn't infer | Send the missing context to the *same* agent — a stopped subagent resumes on a message with its full history intact. Re-dispatching discards that history and re-pays the whole context; do it only if the batch itself changed. |
   | `BLOCKED` | Can't proceed | Assess: too large → split the batch; plan is wrong → escalate to the user; genuinely ambiguous → ask; an auth, permission or safety-check refusal → a path that stays inside the boundary, else escalate to whoever owns it, never another credential or a skip flag. Don't re-dispatch unchanged. |

   **Wrong in KIND reverts; wrong in DEGREE is fixed forward.** Before you respond to a bad batch, say which it is. Built the wrong thing, misread the goal, or diverged from the plan's intent → **revert to the batch's commit and fix the plan**, because every follow-up correction leaves the misreading in context and compounds on it — and batches are sized to roll back as one coherent step for exactly this. A bug, an edge case, a missed assertion → fix forward under **compound-v:systematic-debugging**'s 3-attempt cap. The trap: reverting a batch whose real problem is a bug throws away correct work and re-pays the whole context, so the test is whether the code does the wrong *thing*, never whether it does the right thing badly.

   The status is a clean state machine — act on it, don't re-parse the prose. Then check the *counters*, not just the prose: every subagent returns `toolStats` (`readCount`, `searchCount`, `bashCount`, `editFileCount`, `linesAdded`, `linesRemoved`), and a report describes what the worker intended to do, not necessarily what it did. A `DONE` whose `toolStats` shows zero edits is a `BLOCKED` that lied — treat it as one.
3. Hand the batch to **compound-v:recheck** (one read-only pass over **this batch's diff** — see "Track the batch's range" below) **together with the plan itself**, since that skill's pass is not runnable on a diff alone: its step 2 *is* plan alignment, its deferred-feature grep needs the plan's deferred list, and its step 3 reads the plan's own code snippets with the same suspicion as the diff. Hand over the plan, the spec, and the diff range, and nothing of the implementer's reasoning — first logging any tactic the report says changed as a dated line in the plan's `## Clarifications`, or recheck reads it as divergence. Then take the verdict and the fix↔recheck cycle; that skill owns the three verdicts and the N=3 cap. Nesting is capped, and at the cap the harness withholds the `Agent` tool — so if *this loop is itself running inside a subagent* that cannot dispatch, run the recheck pass inline yourself instead. The one routing rule that lives *here*: an `ARCHITECTURE_CONCERN` (whether on the first pass or after 3 cycles) **stops the loop** — escalate to re-plan (compound-v:writing-plans), never re-dispatch the same batch, and never hand to finishing. Finishing is reachable only from `APPROVED`.
4. On `APPROVED`, **commit the batch**. Mark each task completed in TodoWrite the moment *its* verification passes — don't hold todo updates until the commit; the batch boundary governs the **commit**, not the todo. Git is the state machine, and the thing it has to record is which point was *rechecked* — not merely which point was written. Expect the implementer to have committed as it went: the plan's task template carries a `Commit:` step per task (**compound-v:writing-plans**), and that test-first rhythm is right and worth keeping. Those intermediate commits are work, not verdicts — none of them has been through recheck. So on `APPROVED` the batch's **final** commit is the one that carries the trailer below: make it if there is uncommitted work, and amend it onto the last commit of the range if the implementer already committed everything, rather than manufacturing an empty commit to hold a trailer. Before that commit, re-run the **whole** suite against the setup baseline, not just the tests this batch touched — the range-scoped recheck cannot see what this batch broke in an earlier one, and the trailer you are about to write is the thing that calls the commit verified. Narrow while building, broad before the trailer. That trailer is what promotes a commit from written to verified, so a later batch that breaks the build rolls back to the last known-good point without losing earlier work. When the run carries a state file, that trailered commit is also where **Done** moves (**compound-v:handoff**); the implementer's intermediate commits are exempt from its never-commit-without-moving-the-state-file rule, because they are not yet verified and the state file records what is.

   This is also your **resume protocol**: if the session compacts or restarts mid-plan, reconcile against `git log` before dispatching anything. Resume from the last commit whose trailer names **this plan** — its `Plan:` line, not merely any `Recheck:` line, since an older plan's trailers are still in the log and would otherwise mark unrelated work as yours. That batch is *done*; anything after it is unverified work in progress, so re-verify it rather than trusting it or re-dispatching over it. **If no commit names this plan, nothing is verified yet** — that is the ordinary state of a first batch, so treat everything since this branch diverged (`git merge-base <default-branch> HEAD`, which setup step 2 guarantees exists by making you branch before the first edit) as work in progress and start there rather than concluding the plan never ran (the in-context TodoWrite dies with compaction; the commits don't). Keep the tree mergeable as you go — small, coherent commits, not one giant end-of-plan blob.

   **Put the batch's identity and its verdict in the commit message.** `git log` is the resume oracle above and the durable record this kit already relies on, and neither works if the message is free prose — reconciling a diff back to plan tasks by eye is exactly the re-derivation the resume protocol exists to avoid. Close the batch commit with two trailer lines:

   ```
   Plan: docs/plans/2026-05-04-token-refresh.md tasks 3-5
   Recheck: APPROVED — pytest -q 142 passed, deferred-list grep clean; not assessable: prod config (not in diff)
   ```

   The first line makes resume exact. The second is the one place the review's **negative result** survives: `compound-v:recheck` requires a verdict carrying what it *checked and found clean*, and that is precisely the finding a diff cannot represent — a check that found nothing and a check that never ran leave identical traces in git. One line, in the commit, and both become greppable.

### Track the batch's range
Before dispatching a batch, note the current `HEAD` (`git rev-parse HEAD`). After the implementer reports, the batch's diff is exactly `that-SHA..HEAD` (or the changed-file list from `git diff --name-only that-SHA`). Hand recheck *that* range, so it reviews only this batch and not the whole accumulated branch. The per-batch commit at the end gives you a clean range marker for the next batch.

## Serial by default; parallel only when file-disjoint

Run implementers **serially**; the one exception is batches that are genuinely file-disjoint (no shared files or state), which may fan out — but the gating test and conflict-check-on-return belong to **compound-v:dispatching-parallel-agents**, so defer to it and run serially when unsure.

## Continuous execution

Do not pause between batches to ask "should I continue?" — it wastes the user's turn. The only legal stops are: a `BLOCKED` you can't resolve, a recheck `ARCHITECTURE_CONCERN` (stop the loop, escalate to re-plan), a genuine ambiguity that changes scope, or all batches done and rechecked. Keep going until the plan is built and every batch is APPROVED, then hand off to **compound-v:finishing**.

## Responding to findings

When recheck (or the user) hands back findings for the implementer to fix, the findings are *input to judgment*, not orders to type out:

- **Verify before implementing.** Confirm the finding is real against the actual code — a reviewer can be wrong about what the code does. Fixing a phantom bug adds a real one.
- **Clarify an ambiguous finding before acting** rather than guessing at its intent; a wrong guess costs a whole fix↔recheck cycle.
- **Scan suggestions for scope creep.** A "while you're here, do it properly / handle the general case / add a config for this" finding is often YAGNI — implement what the plan needs, not the gold-plated version, and say why you're deferring it. **A finding you accept but defer past this batch becomes a task in the plan** — the same "task in the plan, not a follow-up" rule `using-compound-v` applies to documentation a change invalidates. Deferred work that lives only in the conversation dies at the next compaction, and unlike a committed batch, git has no record it was ever agreed. In-cycle fixes stay conversational: they go straight back to the same implementer, which already holds the context.
- **No performative agreement.** Don't "you're absolutely right" a finding you haven't checked. If a finding is wrong or out of scope, push back with the reason; that's the value of the loop, not a failure of it.

## Red flags

| Smell | Why it's wrong |
|---|---|
| Implementing on `main`/`master` | No isolation; a bad batch dirties the default branch. Branch first. |
| Re-dispatching a `BLOCKED` batch unchanged | Same input → same block. Change the context, split the batch, or escalate. |
| Skipping recheck "because the batch was simple" | Recheck is the only quality gate in this loop; skipping it removes the gate. |
| Two implementers on shared files in parallel | Merge conflicts and clobbers. Serial unless file-disjoint. |
| Deleting pre-existing dead code, or leaving behind the code the change orphaned | The same slip in opposite directions. Remove what *this diff* stranded — the import, helper or branch it just made unreachable; leave what was already dead, and say you saw it. A drive-by deletion is an unreviewed change riding on an unrelated batch, and it lands hardest on code the implementer didn't fully understand. |
