# Dispatching Parallel Agents

The default is **one agent that does everything**; fan-out is the exception you argue for, not the starting shape. Parallel sub-agents buy exactly two things — wall-clock latency and context isolation. They do *not* buy better answers: whether a multi-agent system beats a single agent given the same resources is unsettled, and fan-out is a latency play, never a token-saving one (a multi-agent run burns on the order of 15× the tokens of a single chat). The default failure isn't too little parallelism, it's splitting coupled work: isolated agents make divergent assumptions and return pieces that don't fit together. Fan out when the seams are clean; otherwise keep it single-threaded.

compound-v:designing-agents decides *whether* to fan out and into which shape (orchestrator-workers, evaluator-optimizer, …); this skill is the *how* once that choice is made. Each sub-agent is a context firewall (compound-v:context-engineering owns that mechanism) — that's why fan-out buys context isolation and not only latency. Reach for a sub-agent only when a piece needs its *own context window*, not merely to run things at once.

## When to fan out

Each piece must earn its own sub-agent, and the set must be safe to run at once. Fan out when **all** of these hold:

- **Breadth-first, not depth-first** — settle the *shape* of the question before the agent count. Breadth-first work splits into independent sub-questions, each answerable on its own; that shape, and only that shape, parallelizes. Depth-first work comes at one question from many angles, and each angle informs the next — run those workers **in sequence**, feeding each the last one's result. Depth-first is the fan-out trap that costs the most: N agents on one topic *looks* parallel and isn't, and the agents come back with N overlapping takes on the same ground.
- **Token-asymmetric** — the piece consumes tens of thousands of tokens and returns something small. That gap *is* the reason to delegate: the worker eats the searches, the reads and the dead ends, and hands back only the conclusion, protecting your context. If the output is about as big as the input, inline it. Concretely: exploration or research that will take more than ~3 queries earns a sub-agent; three or fewer, just run Glob/Grep yourself.
- **Genuinely independent** — task B doesn't need task A's output. (If B consumes A, that's a pipeline, not a fan-out — see below.)
- **Write-disjoint, or worktree-isolated** — agents that write must touch non-overlapping files, or each run in its own worktree (spawn with `isolation: "worktree"` for a temporary git worktree, auto-removed if the agent changes nothing; background sessions *enforce* this and reject edits to the shared checkout until you isolate). Two agents editing the same file is last-write-wins, silently — one agent's work just vanishes. Cut the seam at a *stable interface*, not an arbitrary file boundary, or "disjoint" files still couple through a shared, shifting API. A worktree removes the clobber, not the design divergence, so the coupled-work rule still stands. Fan-out that only *reads* is exempt — deliberately pointing several agents at the same read-only question is a legitimate pattern.
- **Decision-disjoint, not just file-disjoint** — ask whether each agent would have to independently *invent* the same convention. Two agents building disjoint halves of one feature will pick different names, different error shapes, different framings, and the pieces won't fit even though neither touched the other's file. Fix the shared conventions in the brief *before* fanning out, or don't fan out.
- **No shared mutable state — and the git index is shared state.** Worktrees isolate files, not the object store: concurrent `add`/`commit`/`rebase` contend on the same index lock. Every tool built to run coding agents in parallel converged on serializing git mutations, which is the clearest signal in the evidence that file-disjointness alone is not enough. The same goes for anything else global the worktree doesn't clone — a fixed dev-server port, a shared cache or config directory, one test database.
- **No purpose in the first context being part of the second** — the positive test for a seam, and the one that kills the org-chart split. Slicing agents by *role* mirrors a company's reporting lines rather than the problem's structure, and the concrete cost is mutual information: split triage off from the task and the task agent never learns what triage learned beyond the verdict it forwarded, which is typically destructive of value. If you can't say what the second agent is better off *not* knowing, don't split.

**Four measured cautions, because the enthusiasm for this outruns the evidence.** (1) Delegation carries a roughly fixed per-handoff cost — every token crossing the boundary is billed twice — and against a single agent it *lost* until the delegated reading was enormous; at same-model there is no cheaper-worker arbitrage to offset that, so isolation is the only thing it can buy. (2) A fresh worker per unit is the anti-pattern for prompt cache: route repeated work to the *same* worker so its prefix accumulates instead of re-paying the context write each spawn. (3) The split does not remove the best-budget-first pathology, it **relocates** it: position alone moves retrieval by >20% even on i.i.d. data, because primacy is a property of the causal mask rather than of long conversations — so the tail-neglect lands on the one context nobody refreshes, the orchestrator's. (4) A **deterministic** orchestrator is not free either: replacing a reasoning orchestrator with fixed round-robin dispatch cost ~6 points on one benchmark, because routing is only half its job and detecting a stalled or looping worker is the other half. Where fan-out does pay hugely (one benchmark went 57% → 96.5%), the partition was **fixed by a human in advance** and executed by a **deterministic** orchestrator; when the model chose its own fan-out, the same machinery landed at or below one long context at several times the tokens.

Two gates cut the other way. **If you'd have to wait on the sub-agent before doing anything else, don't spawn it** — you've paid the dispatch cost for zero concurrency, so inline the work unless the isolation itself is the payoff (the token-asymmetric case above, where a blocking worker still earns its keep by keeping the dead ends out of your context). **If the pieces would need to talk to each other, don't split them** — no back-channel exists; workers can't reach each other, and anything they'd say has to round-trip through you as a fresh brief. Some work is also structurally non-parallelizable no matter how you slice it: schema migrations, anything bound to a fixed port or a single shared service, and anything whose cwd is the repo root. Run those one at a time and say so rather than discovering it through a corrupted state.

Good fits: editing N unrelated modules, researching N independent sub-questions, processing a batch of independent items, gathering context across disjoint areas of a repo. When unsure, stay single-threaded — the red-flags table below catches the coupled-work case. Note the asymmetry by domain: research fans out cleanly, but **coding has far fewer truly parallel seams** (LLM agents aren't yet great at coordinating in real time), so a multi-file edit is a *weaker* fan-out candidate than it looks — confirm the modules are genuinely decoupled (no shared interface they'd both reshape) before splitting.

### Redundant fan-out: run it N ways, keep one
The independence rules exist so the pieces can be merged; they don't bind when nothing gets merged. Running the *same* task N ways and **discarding N−1 outputs** is a legitimate third case beside the read-only sweep, and the one shape in which a coupled, single-file task parallelizes — it is not the depth-first trap above, which *merges* N takes on one question. Three conditions. **Give each run its own worktree or output path** — discarding the losers later does nothing about collision now, and N writers aimed at one path is last-write-wins: you get one clobbered file, not four candidates. **Seed each run differently** — a prose brief, a visual reference, code lifted from a component library, a working implementation to imitate — because runs off one identical brief share their errors and return one answer N times. And **budget the selection, not the generation**: generating got cheap and curation is now the expensive half, so fix what would make a candidate win *before* you look at them. Left unfixed the pick goes to whichever output looks most finished — a fact about polish, not fit. (To *aggregate* N runs instead of picking one, that's voting: compound-v:designing-agents.)

### Parallelize intelligence; keep writes single-threaded
The sharpest version of the independence rule isn't "which files" but *what kind* of work. Fan-out pays when the extra agents **contribute intelligence — reads, research, critique — while writes stay single-threaded**. Readers can be unlimited: N agents exploring disjoint areas have no way to collide. Writers diverge, and the merge costs more than the fan-out saved. So the canonical safe worker is a **read-only retrieval worker**, and it should be *tool-locked* read-only rather than merely told to be — an agent denied Edit will reach for the shell and write the file anyway. If a step must write, route it through one agent. **The final write is never delegated** — the synthesis, the report, the findings, the decision, whatever the deliverable actually is, stays with the orchestrator, because only it has seen every worker's return. Workers contribute findings; they never produce the artifact you ship, and the harness enforces it: a sub-agent is forbidden to write report/summary/findings/analysis files at all (item 4 below), so a brief that delegates the report comes back empty. **Scope the one carve-out precisely.** A *genuine artifact* — code, a dataset, a generated file — is the worker's to write and hand back as a path; a repo-visible findings, review, or summary document is **not** one of those, however long it is. And where a run does produce such an artifact, an orchestrator 200K tokens deep is badly placed to type it: write the plan yourself first — the thesis, the beats, the per-section commitments — to a file, then hand the *typing* to one fresh, tool-locked worker that executes that plan and may not re-plan. Never delegate a write to avoid deciding.

## Pipeline by default; barrier only when you must merge

Don't block on all workers if you don't have to. If results feed a next stage one at a time, **pipeline** them — start downstream work as each finishes. Use a **barrier** (wait for everything) only when the next step genuinely needs all results together, like a synthesis that reasons over the full set. A premature barrier turns N parallel agents back into the latency of the slowest one for no reason.

## Brief each worker to stand alone

A sub-agent starts with a **fresh, isolated context** — it does *not* see your conversation, the files you've read, or the skills you've invoked. The only thing that crosses the boundary is the prompt string you give it. So every brief must be self-contained. Include:

1. **One clear objective, and a partition that covers the question** — one job per worker; don't bundle. Keep tasks distinct and non-overlapping so two workers never redo or collide on the same thing, then run the test the other way *before* you dispatch: assume every worker executes its brief perfectly, and ask whether the union of those returns would let you write an excellent answer. Non-overlap only prices the waste; the coverage check is what catches the *gap*, and a gap discovered at the barrier costs a whole extra round after every budget is already spent.
2. **All the context it needs — including the part that isn't its slice.** Paths (absolute), the relevant facts, constraints, the spec; it can't ask you mid-run and it can't see what you saw. Err verbose: give every worker the overall picture of what the run is doing and where its piece lands, not just its own sub-task. **One brief is exempt:** a worker researching what is true in this repo for **compound-v:gathering-context** gets the questions, not the goal — with the goal in the room the facts come back as opinions. One production dispatcher composes each brief mechanically as a run-wide shared preamble plus a per-child subtask, and the shared half is exactly what stops N isolated workers each inventing their own framing. The inverse is the tell — if you can't state the whole job well enough to brief the child, you don't know enough to have split it.
3. **How to verify its own work** — the test command to run, the check to pass. A worker that can confirm its result returns something trustworthy.
4. **The return contract** — ask for a tight summary (aim for ≤500 words / ~1–2K tokens): what it did, what it found, what's left, anything that surprised it. Findings cross the boundary; raw dumps do not. **Findings come back as text; artifacts come back as paths.** A sub-agent's own system prompt forbids it to write report/summary/findings/analysis `.md` files and tells it to return findings as its final message — the child obeys that over your brief, so a brief demanding a findings file gets you nothing. Reserve the filesystem handoff for artifacts the task legitimately produces (code, a dataset, a generated file): have the worker write those and **return a lightweight reference (a path)**, which avoids both the lossy re-summarization and the token cost of copying big outputs through the orchestrator's context.

Two structural limits to design around. **Know your harness's real nesting default before you design around it** — Claude Code allows a subagent to spawn its own subagents **three layers deep by default**, and `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` is what turns nesting off. Flat is still the shape you want (a tree you cannot see is a tree you cannot debug, and the orchestrator is the only participant that sees every return), so set the cap deliberately rather than assuming it: at the limit the harness withholds the `Agent` tool from the child, so a worker at the cap inlines the step or hoists it back to you. Separately, a **concurrency cap of 20 running subagents** applies by default — spawning the 21st fails and tells the model not to retry. And many workers each returning verbose results will flood the orchestrator's context, so enforce the condensed-summary contract. **A third limit is not yours to set: a settings chain can switch the execution model under this contract.** Where the harness ships an experimental agent-teams mode (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`), a subagent the model *names* at spawn launches as a teammate instead — holding its own full context window, which voids the asymmetry above, and not restored by session resume, which breaks **compound-v:handoff**'s resume contract mid-run. **The trap: turning it off in your shell loses to a project or managed setting** — read the resolved value, not yours.

## Don't over-spawn

More workers means more overhead and more reconciliation, not linearly more value — and each one is a transcript you can no longer see, so every layer you add makes a failure harder to debug. Prefer **fewer, more capable workers** over many narrow ones; add a worker only when it does something genuinely distinct. A 50-CEO lookup splits cleanly into a handful of workers handling batches — not fifty one-each. Match the count to the real independent seams in the work, and route down to a single agent (or no sub-agent at all) when the task doesn't actually have them. **On worker model tier, hold both halves.** Never downgrade a worker doing substantive implementation — leave the model unset and let it inherit the session model, which is the one the user chose; naming a cheaper tier there silently buys worse code, and the cheap model routinely burns 2–3× the turns anyway, so the saving is often imaginary. The tier split earns its keep only on wide, mechanical, **read-only** sweeps: a frontier model at the orchestration/synthesis layer and a cheaper one across embarrassingly-parallel readers. The headline number for that split — a multi-agent system beating a single frontier agent by ~90% — needs every one of its caveats: it was a **private internal eval scored by an LLM judge against a rubric**, not ground truth and not a public benchmark; it measured **web research**, and the same evidence says most **coding** tasks have far fewer parallelizable parts; it changed two variables at once (fan-out *and* a stronger orchestrator model); and it burned **~3.75× the tokens of the single agent it beat**, on an eval where **token spend alone explained ~80% of the variance**. Read it as an allocation result for retrieval. Nothing in it says more agents buy better answers on coding work — the cheaper reading is that whatever you spend the tokens on, spending them is most of the effect. Price by cost per *successful outcome*, not per token.

**Start at 3. The ceiling is a property of the writes, not of the task.** Where workers touch files or share a design, ~4–5 is the practical ceiling (a frontend / backend / tests / infra split) — one shipped orchestrator refuses the sixth concurrent child outright, and a human supervising the run loses the thread past three to five. A read-only sweep has no such ceiling: one shipped product routes 4 workers at a focused question and 16 at a multi-faceted one off the same prompt and the same toolset, and exhaustive sweeps go wider still by partitioning one worker per input unit rather than per topic. Widening readers costs tokens and a longer synthesis, never a collision — so size a read fan-out to its seams instead of quoting 4 at it. A shipped research orchestrator lands on the same small number from the other direction — it defaults to **3 subagents against a hard cap of 20**, and its own prompt argues itself down: more subagents means more coordination overhead, so add one only when it provides *distinct* value. Beyond a handful you hit the failure mode where workers step on each other's edits and generate incompatible implementations of the same interface, faster than you can reconcile them. The count also scales with the *kind* of task — roughly one worker for a fact-find, a few for a comparison, more only for genuinely broad search — and a lead left to size its own fan-out over-invests: one documented research lead spawned 50 subagents for simple queries until the budget was written into its prompt. Put the worker budget in the brief; don't trust the model to set it. File-ownership discipline fixes the collisions, but the cheaper fix is *not spawning the extra workers in the first place*.

## Runtime budgets and the synthesis barrier

An unbounded worker is a hang waiting to happen. Give each one a budget and make the barrier tolerant of a worker that blows it:

- **Per-worker step/tool cap.** Bound how many tool calls or steps a worker may take before it must return what it has. A worker that can loop forever will, on the one input that confuses it — and it takes the whole batch's latency hostage.
- **Per-worker timeout → soft-fail at the barrier.** When you wait for all workers (a synthesis barrier), don't block indefinitely on the slowest. Set a per-worker deadline; if one misses it, **proceed with the partial results and note the gap** rather than hanging the whole fan-out on one stuck agent. Best-so-far beats never-returns.
- **Ask the set-level question at the barrier — no worker can answer it.** A verifier judging one returned item is asked *is this true?*, and a duplicate passes that honestly, twice: its twin sits in a sibling's return, not in anything either worker could read. So two defects survive any per-item gate — **duplication across workers**, and **a resurrection of something an earlier round already rejected and therefore left absent**. Neither is a strictness failure, so a harsher verifier reaches neither; both are properties of the pooled set. Dedupe the returns against each other before acting on any of them, and carry a list of what previous rounds killed into the pool or it comes back under a new name. Measured here: a fan-out whose per-item verifiers passed 28 of 30 lost four to cross-worker duplication and one to a resurrection, every one found only by pooling.
- **A pending-set guard against double-dispatch.** The orchestrating model will sometimes re-dispatch a worker it already launched (it forgets, or a retry fires twice). Track in-flight jobs in a pending set and refuse a duplicate with a recoverable message ("already running") — otherwise two agents do the same write and you're back to last-write-wins.

## Red flags

| Symptom | What it means |
|---|---|
| Two workers *write* the same file | Not write-disjoint — one will silently overwrite the other. Re-partition, isolate in worktrees, or serialize. |
| A worker needs another worker's output — or N workers hit one question from N angles | Pipeline dependency, or depth-first work wearing a fan-out costume. Sequence them; feed each the last one's result. (Not the redundant-fan-out case above: that one *discards* N−1 rather than merging them.) |
| Briefs reference "the file we just looked at" | The worker can't see it — fresh context. Inline the content or the absolute path. |
| Spawning a worker per tiny item | Over-spawn. Batch items per worker; prefer fewer capable workers. |
| Blocking on all workers before any next step | Premature barrier. Pipeline unless the next step truly needs the full set. |
| The same worker dispatched twice | Double-dispatch. Guard with a pending set; refuse the duplicate. |
| The barrier hangs on one slow worker | No per-worker timeout. Soft-fail it and synthesize the partial results. |
| Splitting a tightly-coupled design across agents | Coupled work — they'll diverge, *unless nothing is merged* (see Redundant fan-out). Otherwise keep it single-threaded; if it must be split, serialize it through a shared handoff file — one agent writes its state to a markdown file the next one reads. |
